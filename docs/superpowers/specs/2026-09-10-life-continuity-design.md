# 人生连续性与姓名家庭规则设计

## 1. 目标

在不重写现有人生引擎的前提下，让玩家每年的经历更明显地受到此前人生经历影响，并修复自定义姓名与父母姓氏、重复求职文案不一致的问题。

核心目标：
- 让过去 1～10 年的重要经历影响后续事件进入概率、事件文案和可选方向。
- 让职业、城市、家庭、健康、NPC、创业等主线形成自然的连续剧情。
- 保留随机性，避免人生被早期选择完全锁死。
- 复用现有 `history / memories / tags / npcs / careerHistory / cityHistory / scheduled`，只增加一个轻量回声计数对象，不新建复杂持久化系统。
- 不调用运行时 AI API。

## 2. 已确认规则

### 2.1 自定义姓名与父母姓氏

- 玩家输入可识别的中文姓名时，取第一个汉字作为玩家姓氏。
- 父亲必须使用玩家姓氏。
- 母亲保留随机姓氏，不强制与玩家同姓。
- 玩家未输入姓名时，继续沿用现有随机姓氏与随机姓名生成逻辑。
- 玩家输入英文、数字、符号或无法可靠识别中文姓氏时，不强行截取，回退到现有随机姓氏逻辑。
- 出生事件文案继续使用最终生成后的父母姓名。

示例：玩家输入“王小明” → 父亲姓王，母亲随机姓氏。

## 3. 人生连续性机制

采用“通用连续性评分 + 少量强剧情链”的混合方案。

### 3.1 四层记忆来源

1. 短期记忆：过去 1～3 年历史事件，影响最强。
2. 中期记忆：过去 4～10 年重大经历，保留中等影响。
3. 长期身份：`tags`、当前/历史职业、城市履历、婚姻、子女、房产、负债、长期伤病、人生愿望等长期状态。
4. 人物记忆：`npcs[].experiences`、关系值、信任值、职业、所在城市等。

### 3.2 统一连续性评分

在 `dist/engine/event.js` 增加集中式 `continuityScore(event, state)`，只负责计算“这个事件和玩家过去人生有多相关”。

建议范围：
- 最近 1～3 年直接关联：+30～60
- 4～10 年重要经历：+10～30
- 长期身份匹配：+5～25
- 同职业、同城市、同 NPC、同家庭主题、同长期标签均可参与
- 明确强后续链：乘数 ×2～×4

概念公式：

`最终权重 = 现有基础权重 × 现有城市/兴趣修正 × 强后续倍率 + 连续性加分`

之后继续执行现有的近几年同类事件降权和职业类别重复惩罚。

### 3.3 随机性保留

- 连续性加权设置上限，防止单一主线吞掉全部事件。
- 设计目标约 65% 偏向玩家既往人生，35% 保留意外性；这是体验目标，不做硬概率分流。
- 普通日常事件不强制配置连续性字段。

## 4. 事件数据结构扩展

仅新增可选字段，不改现有事件基础结构。

建议字段：
- `historyLinks`：与历史事件 ID、类别、职业、城市、标签等的弱关联。
- `followUpOf`：明确的强前置事件列表。缺少前置时，该事件不进入候选池。
- `memoryWeights`：声明哪些历史状态可额外加权。
- `echoText`：用于插入“过去经历回声”的预写模板。

不要求全部 107 个事件补字段。第一版只改 20～30 个关键事件。

## 5. 回声消费限制

同一重大历史经历不能无限触发后续。

实现规则：
- 玩家状态新增轻量对象 `echoUsage`，默认 `{}`。
- key 使用历史来源稳定标识：`${eventId}:${age}`。
- value 为该条历史经历已触发的“强回声”次数。
- 单条重大经历最多触发 3 次强回声。
- 达到 3 次后，仍可保留轻微连续性权重，但不再获得 `followUpOf` 强倍率。
- 旧存档不存在 `echoUsage` 时按 `{}` 处理。

不新增大型索引或独立数据库。

## 6. 第一版重点剧情链

### 6.1 求学 → 第一份工作 → 职业发展
- 专业、资格、爱好、父母职业、NPC 职业继续影响求职。
- 上一份职业加入后续求职评分。
- 晋升、转岗、转行、旧同事事件更偏向当前/历史职业经历。

### 6.2 迁居 → 适应 → 新机会
- 迁居后 1～3 年提高城市适应、生活成本、新社交、当地工作机会权重。
- 多年后允许出现原城市旧友、回乡、旧城市机会。

### 6.3 恋爱 → 结婚 → 子女 → 家庭压力
- 伴侣和子女状态进入家庭事件权重。
- 婚后事件优先引用真实伴侣和家庭状态。

### 6.4 创业 → 成败 → 债务 / 再创业 / 旧合伙人
- 创业成功、失败、破产、债务、旧合伙人适合作为强 `followUpOf`。
- 无创业历史时，强后续事件不得进入事件池。

### 6.5 健康 → 治疗 → 长期影响
- 严重疾病、工伤、治疗结果影响未来几年健康与职业事件。
- 长期健康标签参与后续权重。

### 6.6 NPC → 重逢 → 合作 / 冲突 / 告别
- 优先复用已有 NPC，而不是重复生成新角色。
- `npcs[].experiences` 决定重逢和合作文案。
- 明显回声次数受限制。

## 7. 求职事件修复

当前 `job_search` 标题固定为“第一份工作的方向”，但该事件同时被毕业、失业、创业失败、工伤后转行等场景复用，因此会在后续求职时重复显示“第一份工作”。

### 7.1 动态标题与文案

在 `builder: 'jobs'` 的物化阶段，根据 `careerHistory` 判断：

- `careerHistory.length === 0`：
  - 标题固定为 `第一份工作的方向`
  - 文案保留初次求职语义。

- `careerHistory.length > 0`：
  - 标题固定为 `重新寻找工作`
  - 文案引用上一份职业、当前城市和最近离职/失败背景。

示例：
- “上一份工作结束后，你重新整理了履历……”
- “离开软件行业岗位后，你开始重新评估下一份工作的方向……”

再次求职时不得再出现“第一份工作”字样。

### 7.2 求职权重连续性

再次求职时：
- 上一份职业的相邻转型职业获得加权。
- 当前专业、资格、职业能力继续生效。
- 当前城市产业权重继续生效。
- 如果是创业失败后求职，可对销售、运营、管理、原行业等合理方向加权。
- 不强制玩家回到原职业，仍保留跨行机会。

## 8. 文件与职责边界

预计实现时主要修改：

- `dist/state/player.js`
  - 自定义姓名姓氏解析与父亲姓氏生成。
  - 初始化 `echoUsage: {}`。

- `dist/engine/event.js`
  - `continuityScore`
  - 强后续资格判断
  - 求职动态标题/文案
  - 上一职业与历史经历参与求职评分

- `dist/data/events.js`
  - 给第一批 20～30 个关键事件增加连续性元数据。
  - 不大规模重写已有事件。

- `dist/engine/memory.js` / `dist/engine/effect.js`
  - 仅在强回声实际发生后更新对应 `echoUsage` 计数。

- `tests/core.test.js` 或新增 `tests/continuity.test.js`
  - 回归测试。

禁止无关重构。

## 9. 数据流

每年事件选择流程：

1. 按现有条件筛选事件。
2. `materialize()` 生成动态事件内容。
3. 计算现有基础权重、城市、兴趣等修正。
4. 计算 `continuityScore()`。
5. 检查 `followUpOf` 前置条件和 `echoUsage` 次数。
6. 应用连续性权重。
7. 执行现有近几年同类事件降权。
8. 使用现有加权随机选择事件。
9. 事件结果继续通过 effect/memory 引擎写入状态；若消费了强回声，再递增对应 `echoUsage`。

不改变固定种子随机机制。

## 10. 错误与兼容处理

- 旧存档没有 `echoUsage` 时必须正常运行并按空对象处理。
- 新事件字段全部为可选。
- 无历史记录时 `continuityScore` 返回 0，不影响原事件池。
- 找不到前置事件时强后续直接不入池，不抛异常。
- 无 NPC 或已死亡 NPC 不作为人物回声目标。
- 自定义姓名无法识别中文姓氏时回退随机姓氏，不阻止创建人物。
- 固定种子复现能力必须保持。

## 11. 测试要求

至少覆盖：

1. 自定义“王小明”时父亲姓王。
2. 母亲不被强制姓王。
3. 英文/非法姓名输入时姓氏逻辑正常回退。
4. 第一次求职显示“第一份工作的方向”。
5. 已有职业履历再次求职标题为“重新寻找工作”，且任何文案不再出现“第一份工作”。
6. 有相关历史时，关联事件权重明显高于无相关历史状态。
7. 缺少 `followUpOf` 前置时强后续事件不进入候选池。
8. `echoUsage` 达到 3 次后不再获得强后续倍率。
9. 上一份职业影响再次求职候选排序，但不会完全锁死职业方向。
10. 固定种子仍能完整复现人物与人生。
11. 现有七城市完整人生测试保持通过。
12. 旧存档缺失 `echoUsage` 时可继续推进人生。

## 12. 第一版范围限制

第一版不做：
- 运行时 AI 自动生成剧情。
- 每个事件都配置复杂事件图。
- 新建大型关系数据库或图结构。
- 一次性扩充到数百条连续剧情事件。
- 改写现有年份推进、存档和纵向滑页交互。

第一版只建立可复用的连续性框架，并让 20～30 个高价值事件率先获得明显剧情回声。
